# מפרט מערכת ניהול לעסק התכשיטים

> מסמך תכנון — גרסה 2, אחרי תשובות על שאלות הפתיחה.
> נבנה באותה שיטה שבה נבנתה מערכת ה-CRM של סוכנות השחקנים.

---

## 0. מה השתנה מגרסה 1

התשובות שלך שינו את התוכנית בארבע נקודות מהותיות:

| מה חשבנו | מה בפועל | ההשלכה |
|---|---|---|
| מלאי חומרי גלם מלא עם תנועות ופחת | "מספר מוצרים בודד" | **מלאי חומרי גלם יורד מהתוכנית.** רשימת אבנים פשוטה מספיקה. |
| נבנה מנוע תמחור מאפס | כבר יש מחשבון עובד | **המחשבון הופך לליבת המערכת**, לא נבנה מחדש. |
| מלאי = ניהול מחסן | "מלאי של תמונות ומוצרים בווטסאפ ואונליין" | **קטלוג עם תמונות ועמוד שיתוף** עולה לראש התוכנית. |
| מע"מ אחיד | חלק בארץ עם מע"מ, חלק לחו"ל | **דגל ייצוא** בכל הזמנה שמאפס מע"מ. |

**נפח:** 1–4 הזמנות בשבוע. זה מכתיב מערכת רזה — כל מנגנון שדורש הזנה יומית ידנית ייזנח.
המערכת חייבת לחסוך זמן מהיום הראשון, לא ליצור עבודת הזנה.

## 1. שיטת העבודה

1. **מפרט בעברית לפני קוד.** אתה מאשר, ורק אז בונים.
2. **גרסה ראשונה שלמה** — עובדת מקצה לקצה, לא שלד.
3. **הרחבה בשכבות** — כל תוספת היא קומיט אחד נקי.
4. **סטאק:** Next.js 16 + TypeScript + Tailwind (RTL) + SQLite דרך Drizzle,
   קובץ `jewelry.db` יחיד. מקומי עכשיו, מוכן לענן.
5. **פרויקט נפרד** מ-SFG_PLAYER_CRM. המסמך הזה יושב כאן רק כתיעוד.

## 2. מנוע התמחור — הליבה

הבסיס: המחשבון **"מאזני תמחור"** שכבר בנית. הלוגיקה שלו עוברת למערכת כפי שהיא.

### 2.1 שערים גלובליים (`rates`)
| שדה | דוגמה | מקור |
|---|---|---|
| `gold_spot_usd_oz` | מחיר זהב 24K לאונקיית טרוי | Kitco |
| `fx_usd_ils` | שער יציג | בנק ישראל |
| `vat_pct` | 18 | |
| `updated_at` | | |

השערים נשמרים בהיסטוריה. **כל הזמנה והצעה מצלמות את השער ביום שלהן** —
אחרת אי אפשר לדעת אם הרווחת או שהזהב פשוט עלה.

### 2.2 טבלת קראט (קבוע במערכת)
| קראט | טוהר (fine) |
|---|---|
| 24K | 999 |
| 22K | 916 |
| 21K | 875 |
| 18K | 750 |
| 14K | 585 |
| 9K | 375 |

```
מחיר זהב לגרם ($) = ספוט לאונקיה ÷ 31.1034768 × (טוהר ÷ 999)
```

### 2.3 חישוב עלות פריט
```
עלות זהב        = משקל בגרמים × מחיר לגרם לפי קראט
+ אבן מרכזית    = מחיר לקראט × משקל כולל בקראט
+ אבני צד       = מחיר לקראט × משקל כולל בקראט        [ניתן לכיבוי]
+ מחיר מודל                                            [ניתן לכיבוי]
+ עבודת צורף
+ שיבוץ מרכזית  = מחיר לאבן × כמות
+ שיבוץ צד      = מחיר לאבן × כמות                     [ניתן לכיבוי]
+ רודיום + קופסא + שקית + אריזה
─────────────────────────────────
= עלות כוללת ($)      →  ₪ = $ × שער יציג
```

### 2.4 מדרגות מחיר
מכפילים על העלות: `×1.3` · `×1.6` · `×2` · `×2.5` · `×3` — כל אחד מוצג
לפני ומכולל מע"מ, בדולר ובשקל. המכפילים ניתנים לעריכה.

> **הערה עסקית שכדאי לתקן במחשבון:** מה שמסומן היום כ"רווח 30%" הוא **תוספת 30% על העלות**,
> ושיעור הרווח בפועל ממחיר המכירה הוא **23%**. ×1.6 נותן רווח של 37.5%, ×2 נותן 50%.
> ההצעה: להציג את שני המספרים זה לצד זה — *מכפיל* ו*שיעור רווח בפועל* —
> כדי שלא תתמחר בטעות נמוך ממה שהתכוונת.

### 2.5 מטבע ומע"מ
- **מטבע הבסיס הוא דולר.** זהב ואבנים מתומחרים בדולר, ולכן כל העלויות נשמרות בדולר
  עם צילום שער ההמרה. מחיר ללקוח נשמר במטבע שבו נסגרה העסקה.
- לכל הזמנה יש דגל **`is_export`**:
  - **בארץ** → מע"מ מלא לפי `vat_pct`, חשבונית רגילה.
  - **ייצוא** → **מע"מ 0%**, ההזמנה מסומנת כעסקת ייצוא, ושדה למספר מסמך הייצוא.
- מתג נפרד ל**מע"מ על העלות** (מע"מ ששולם על חומר מיובא) — כמו במחשבון היום.

## 3. מודל הנתונים

### 3.1 ליבה

**`customers` — לקוחות**
שם, סוג (`פרטי` / `חנות` / `מפיץ`), טלפון, וואטסאפ, מייל, אינסטגרם, מדינה,
כתובת, מקור הגעה, מי המליץ, האם ייצוא כברירת מחדל, הערות, סטטוס.
_(תאריכים חשובים — יום נישואין וכו' — בטבלה נלווית, לשלב מאוחר.)_

**`orders` — הזמנות**
| שדה | הערות |
|---|---|
| `order_number` | מספר רץ |
| `customer_id` | |
| `type` | `בהזמנה` / `ממלאי` / `תיקון` / `שינוי מידה` |
| `channel` | `וואטסאפ` / `אינסטגרם` / `המלצה` / `אתר` / `פנים אל פנים` |
| `is_export` | דגל ייצוא — מאפס מע"מ |
| `status` | ראה 4 |
| `event_date`, `promised_date`, `internal_due_date`, `delivered_at` | |
| `fx_snapshot`, `gold_spot_snapshot`, `vat_snapshot` | צילום שערים |
| `total_usd`, `total_ils`, `vat_amount`, `currency` | |
| `green_invoice_number` | מספר החשבונית שהופקה בחשבונית ירוקה |
| `notes` | |

**`order_items` — פריטי הזמנה**
מכיל את **כל שדות המחשבון**: שם, סוג פריט, קראט, משקל זהב, אבן מרכזית
(סוג, מחיר לקראט, קראט, תיאור), אבני צד (אותו דבר + מתג), מחיר מודל (+ מתג),
עבודת צורף, שיבוץ מרכזית (מחיר × כמות), שיבוץ צד (מחיר × כמות), רודיום,
קופסא, שקית, אריזה — ובנוסף: מידה, חריטה, גוון מתכת, כמות, `cost_usd` מחושב,
מכפיל שנבחר, `price` סופי, `product_id` אם הגיע מהקטלוג.

> פריט הזמנה = בדיוק כרטיס הפריט של המחשבון. אותם שדות, אותו חישוב, אותו פלט.

### 3.2 קטלוג — המטרה שהצהרת עליה

**`products` — מוצרים**
| שדה | הערות |
|---|---|
| `sku`, `name`, `category` | |
| `description` | הטקסט שנשלח ללקוח |
| `photos` | **מספר תמונות, עם תמונה ראשית** |
| `spec` | קראט, משקל ממוצע, אבנים סטנדרטיות |
| `cost_usd` | מחושב במנוע התמחור |
| `price_retail`, `price_wholesale` | |
| `is_published` | האם מופיע בעמוד השיתוף |
| `is_available` | קיים פיזית / לפי הזמנה |
| `times_sold` | מה באמת עובד |

**ייבוא ראשוני:** ה"מלאי מתומחר" ששמור היום ב-localStorage של המחשבון
נטען למערכת כקטלוג ההתחלתי. אין הקלדה מחדש.

**`collections` — קולקציות**
קיבוץ מוצרים לשליחה: "טבעות אירוסין", "מבחר ללקוחה X", "קולקציית חורף".

### 3.3 מפעלים

**`suppliers`** — כולם חיצוניים: מפעל יציקה, משבץ, מצפה, ספק אבנים, ספק זהב.
שם, איש קשר, וואטסאפ, זמן אספקה ממוצע, תנאי תשלום, דירוג פנימי.

**`work_orders` — הזמנות עבודה**
`order_item_id`, `supplier_id`, מה מבקשים, תאריך שליחה, תאריך יעד,
`metal_sent_g` / `metal_returned_g` / `waste_g`, עלות, סטטוס,
`factory_eta`, `access_token`.

**`work_order_updates`** — כל עדכון מהמפעל: סטטוס, טקסט, תמונות, תאריך.

### 3.4 כסף

**`payments`** — סוג (`מקדמה` / `ביניים` / `סופי` / `החזר`), סכום, מטבע,
תאריך, אמצעי, אסמכתא, מספר חשבונית ירוקה.
**יתרה לגבייה** = סה"כ ההזמנה פחות סכום התשלומים.

**`expenses`** — הוצאות שוטפות, לרווחיות ברמת העסק.

### 3.5 תשתית
`tasks` (משימות) · `timeline_events` (יומן לכל הזמנה ולקוח) ·
`files` (סקיצות, רנדרים, תעודות אבנים) · `stones` (רשימת אבנים במלאי — פשוטה) ·
`user` (משתמש יחיד עם סיסמה).

## 4. מסלול ההזמנה

```
פנייה → הצעת מחיר → אושר + מקדמה → עיצוב → אישור עיצוב → ייצור במפעל
   → שיבוץ → גימור וציפוי → בקרת איכות → מוכן → נמסר/נשלח → תשלום סופי → סגור
```
מצבים חוצי־מסלול: `בהמתנה ללקוח` · `בהמתנה לחומר` · `בתיקון` · `הוחזר` · `בוטל`.

כל מעבר נרשם עם תאריך, כדי לענות על "כמה זמן באמת לוקח" ו"איפה נתקעים".

## 5. הדפים שפונים החוצה

### 5.1 פורטל מפעל — `/factory/[token]`
כל המפעלים חיצוניים, ולכן זה הדף הכי חשוב במערכת.
קישור שנשלח בוואטסאפ, בלי סיסמה ובלי אפליקציה.

**המפעל רואה:** מפרט טכני מלא, סקיצות ותמונות, כמה זהב נשלח, מה מבקשים, תאריך יעד.
**המפעל מעדכן:** סטטוס, ETA, תמונות התקדמות, הערות.
**המפעל לא רואה:** מחיר ללקוח, שם הלקוח, רווחיות, עבודות של מפעלים אחרים.

### 5.2 עמוד שיתוף מוצר / קולקציה — `/p/[slug]`
**זה מה שהופך את הקטלוג לכלי מכירה.** עמוד נקי עם תמונות המוצר, מפרט,
מחיר (או "לפנייה"), וכפתור פנייה בוואטסאפ. אתה שולח לינק אחד בוואטסאפ במקום
שבע תמונות ושלוש הודעות.
- לינק לקולקציה = מבחר מותאם ללקוחה מסוימת.
- אפשרות לעמוד עם מחיר או בלי, לפי לקוח.

### 5.3 עמוד לקוח — `/order/[token]`
ציר זמן של ההזמנה, תמונות עיצוב, כפתור "אני מאשר את העיצוב", יתרה לתשלום.

## 8. עקרונות

1. **עברית מלאה ו-RTL** בכל מסך.
2. **סיסמה מהיום הראשון** — משתמש יחיד, הרשאות מרובות משתמשים בהמשך.
3. **צילום שערים בזמן אמת** — זהב, דולר ומע"מ נשמרים כפי שהיו ביום העסקה.
4. **דולר הוא מטבע העלות**, שקל הוא מטבע התצוגה בארץ.
5. **ייצוא מאפס מע"מ אוטומטית** — לא סומכים על זיכרון.
6. **המפעל רואה מפרט בלבד.**
7. **אין הזנה כפולה.** מה שהוקלד במחשבון לא מוקלד שוב בהזמנה.
8. **גיבוי = קובץ אחד** — `jewelry.db` לדרייב.

## 9. מה נשאר לסגור

1. **עדכון שער הזהב** — ידני יומי, או משיכה אוטומטית? (אוטומטי דורש חיבור רשת ומקור מחיר)
2. **מכפיל ברירת מחדל** — באיזו מדרגה אתה מוכר בפועל ברוב המקרים?
3. **מקדמה** — אחוז קבוע, או משתנה לפי הזמנה?
4. **עמוד השיתוף** — מחירים גלויים לכולם, או "לפנייה" וכל לקוח מקבל לינק עם המחיר שלו?
5. **תמונות** — כמה תמונות למוצר בממוצע, ומאיפה הן מגיעות (טלפון, צלם, רנדר)?
