# מפרט מערכת ניהול לעסק התכשיטים

> מסמך תכנון — הגרסה שמאושרת לפני שנכתבת שורת קוד ראשונה.
> נבנה באותה שיטה שבה נבנתה מערכת ה-CRM של סוכנות השחקנים.

---

## 0. שיטת העבודה (מה שעבד בכדורגל)

1. **מפרט בעברית לפני קוד.** מגדירים ישויות, שדות וסטטוסים. אתה מאשר. רק אז בונים.
2. **Phase 1 מצומצם אבל שלם.** עובד מקצה לקצה מהיום הראשון — לא שלד ריק.
3. **הרחבה בשכבות.** כל תוספת = קומיט אחד נקי (טאב חדש, ישות חדשה, הרשאות, תזכורות).
   בכדורגל התחלנו ב-3 טבלאות והיום יש 21 — אבל אף פעם לא בנינו הכל בבת אחת.
4. **סטאק זהה:** Next.js 16 + TypeScript + Tailwind (RTL מלא) + SQLite דרך Drizzle,
   קובץ `jewelry.db` יחיד. גיבוי = העתקת קובץ. מקומי עכשיו, מוכן לענן בהמשך.

**החלטה:** המערכת תיבנה כ**פרויקט נפרד** (`SFG_JEWELRY` או שם אחר), לא בתוך מערכת השחקנים.
המסמך הזה יושב כאן רק כתיעוד התכנון; הקוד ייפתח ברפו חדש.

## 1. מפת העסק — ארבעה ערוצים, מנוע אחד

| ערוץ | איך זה מתחיל | איך זה נגמר |
|---|---|---|
| **הזמנה אישית** | פנייה של לקוח → הצעת מחיר → אישור + מקדמה | ייצור במפעל → מסירה → תשלום סופי |
| **מכירה קמעונאית** | לקוח בוחר פריט קיים מהמלאי | מכירה מיידית → הפריט יורד מהמלאי |
| **סיטונאות לחנויות** | הזמנה של חנות / קונסיגנציה | אספקה → חשבונית → תנאי תשלום שוטף |
| **אונליין** | ליד מאינסטגרם / אתר / מרקטפלייס | הזמנה + משלוח |

הכל מתנקז לשתי ישויות מרכזיות: **לקוח** ו**הזמנה**.
ההבדל בין הערוצים הוא `order.channel` ו-`order.type`, לא מערכת נפרדת לכל ערוץ.

### 2.4 סטטוסים — מסלול ההזמנה

```
פנייה  →  הצעת מחיר  →  אושר + מקדמה  →  עיצוב/סקיצה  →  אישור עיצוב ע"י הלקוח
   →  CAD / דגם  →  יציקה במפעל  →  שיבוץ אבנים  →  ליטוש וגימור  →  ציפוי
   →  בקרת איכות  →  מוכן לאיסוף  →  נמסר/נשלח  →  תשלום סופי  →  סגור
```
סטטוסים חוצי-מסלול: `בהמתנה ללקוח`, `בהמתנה לחומר`, `בוטל`, `בתיקון`, `הוחזר`.

כל שינוי סטטוס נרשם ב-**`order_status_history`** (מי, מתי, מאיזה סטטוס, הערה) —
כדי לענות על "כמה זמן באמת לוקח לי לייצר טבעת" ו"איפה נתקעים".

### 2.7 מלאי — שתי שכבות

**`inventory_items` — פריטים מוכנים** (כל פריט פיזי בנפרד, עם serial)
`product_id`, `serial`, מתכת, משקל בפועל, אבנים, `cost`, `price`,

`status` (`במלאי` / `בקונסיגנציה` / `שמור ללקוח` / `נמכר` / `הוחזר`), תמונות.

**`materials` — חומרי גלם**
| סוג | יחידה | דוגמה |
|---|---|---|
| מתכת | גרם | זהב 18K לבן |
| אבן | קראט / יחידה | יהלום 0.30ct G VS1 |

**`material_transactions` — תנועות מלאי**

שדות: `material_id`, כמות (+/-), עלות, `order_id` / `purchase_id`, תאריך, מי ביצע, הערה.
היתרה תמיד = סכום התנועות. אין "עריכת מספר ידנית" בלי תנועה — ככה המלאי לא משקר.

**`purchases` — רכש מספקים**
ספק, תאריך, מספר חשבונית, שורות (חומר, כמות, עלות), סה"כ, סטטוס תשלום.

### 2.8 תמחור ורווחיות

**`metal_prices` — שערי מתכת**
`metal_type`, `price_per_gram`, `date`, מקור (ידני / API).
כל הצעה והזמנה **מצלמות את השער ביום שלהן** — אחרת רווחיות היסטורית חסרת משמעות.

**חישוב עלות פריט (אוטומטי):**
```
עלות מתכת   = משקל בפועל × מחיר לגרם (לפי קראט)  ×  (1 + % פחת)
עלות אבנים  = סכום עלויות מ-item_stones
עלות עבודה  = סכום cost מכל ה-work_orders של הפריט
עלות נוספת  = ציפוי + חריטה + תעודה + משלוח
─────────────────────────────────────────
עלות ישירה  = הסכום
+ תקורה     = עלות ישירה × overhead_pct  (מוגדר בהגדרות)
= עלות מלאה
רווח        = מחיר מכירה − עלות מלאה
% רווח      = רווח / מחיר מכירה
```
מוצג **בכל הזמנה, בכל פריט, ובדוח חודשי** — כולל "הדגמים הכי רווחיים" ו"הזמנות שהפסדתי בהן".

**`expenses` — הוצאות** (שכירות, פרסום, שילוח, אריזה, רו"ח) — לרווחיות אמיתית ברמת העסק.

### 2.9 כסף

**`payments` — תשלומים**
`order_id`, סוג (`מקדמה` / `תשלום ביניים` / `תשלום סופי` / `החזר`), סכום, תאריך,
אמצעי (`מזומן` / `אשראי` / `העברה` / `ביט` / `פייפאל` / `צ'ק`), מספר אסמכתא,
`invoice_number` (חשבונית שהופקה), הערות.

**יתרה לגבייה** = `order.total` − סכום התשלומים. מוצגת בהזמנה, בכרטיס הלקוח, ובדשבורד.

**`receivables` (תצוגה, לא טבלה)** — כל ההזמנות עם יתרה > 0, ממוינות לפי כמה זמן פתוח.

### 2.10 תשתית רוחבית

- **`tasks`** — משימות (כותרת, יעד, דחיפות, משויך ל, קשור להזמנה/לקוח). כמו בכדורגל.
- **`timeline_events`** — יומן אירועים לכל הזמנה ולקוח (שיחה, מייל, פגישה, שינוי סטטוס).
- **`files`** — תמונות וסקיצות, קבצי CAD, תעודות אבנים, חשבוניות, תעודות אחריות.
- **`users` + `permissions`** — מנהל / עובד / צופה / מפעל. תבנית `crm_users` מהכדורגל.
- **`shipments`** — חברת שילוח, מספר מעקב, סטטוס, ביטוח (חשוב בתכשיטים).
- **`consignments`** — פריטים אצל חנות: מתי נמסרו, עד מתי, מה נמכר, מה חוזר.

## 3. מסכים

### דשבורד (המסך שנפתח בבוקר)
- הזמנות לפי שלב — עמודות עם ספירה
- **מסירות השבוע** + הזמנות שעברו את התאריך המובטח (אדום)
- הזמנות שתקועות במפעל מעל X ימים
- יתרות לגבייה + מקדמות שלא נגבו
- מלאי חומרי גלם מתחת לסף
- פניות שלא טופלו
- הצעות מחיר שפגות השבוע
- רווח החודש מול החודש שעבר

### הזמנות
לוח **קנבן לפי שלב** (גרירה משנה סטטוס) + תצוגת טבלה עם סינון וחיפוש.

### עמוד הזמנה — טאבים
`פרטים` · `פריטים ואבנים` · `עיצוב ותמונות` · `מפעל וייצור` · `תמחור ורווחיות` ·
`תשלומים` · `יומן ותקשורת` · `מסמכים`
_(אותו רעיון של 11 הטאבים בפרופיל שחקן.)_

### שאר המסכים
לקוחות · כרטיס לקוח (הזמנות, תשלומים, תאריכים חשובים, יומן) · פניות · הצעות מחיר ·
קטלוג דגמים · מלאי פריטים · חומרי גלם + תנועות · רכש · ספקים ומפעלים ·
הזמנות עבודה · כספים (גבייה, תשלומים, הוצאות) · דוחות · משימות · הגדרות.

## 4. הדפים שפונים החוצה

### 4.1 פורטל מפעל — `/factory/[token]`
הצורך שסימנת: *"דף פירוט הזמנה שהמפעל שלי מקבל ומעדכן סטטוס התקדמות"*.

**שלב א' — קישור לכל הזמנת עבודה** (כמו עמוד השאלון של השחקנים):
המפעל מקבל לינק בוואטסאפ. בלי סיסמה, בלי אפליקציה. רואה:
מפרט הפריט, סקיצות ותמונות, משקל זהב שנשלח, מה בדיוק מבקשים, תאריך יעד.
מעדכן: סטטוס, ETA, הערות, **העלאת תמונות התקדמות**.
כל עדכון נכנס ל-`work_order_updates` ומקפיץ התראה אצלך.

**שלב ב' — פורטל מפעל עם התחברות:** רשימת כל העבודות הפתוחות של אותו מפעל במקום אחד.

**מה המפעל לא רואה:** מחיר ללקוח, שם הלקוח, רווחיות. רק המפרט הטכני.

### 4.2 עמוד לקוח — `/order/[token]`
הלקוח רואה: איפה ההזמנה עומדת (ציר זמן ויזואלי), תמונות עיצוב,
כפתור **"אני מאשר את העיצוב"**, תאריך אספקה משוער, יתרה לתשלום.
מוריד לך חצי מהוואטסאפים של "מה קורה עם הטבעת?".

### 4.3 טופס פנייה מהאתר (שלב מאוחר יותר)
לקוח ממלא בקשה → נכנס אוטומטית כ-`inquiry`.

## 6. עקרונות שנשמור עליהם

1. **עברית מלאה ו-RTL** בכל מסך — כמו במערכת השחקנים.
2. **אין מחיקה שקטה.** מחיקה = אישור כפול. מידע כספי לא נמחק, מסומן כמבוטל.
3. **צילום מחיר בזמן אמת.** שער זהב, עלות אבן, עלות עבודה — נשמרים כפי שהיו ביום העסקה.
4. **המלאי זז רק בתנועות.** אין תיקון ידני של יתרה.
5. **המפעל רואה רק מפרט טכני.** לא מחירים, לא לקוחות.
6. **מקומי קודם, מבנה שמאפשר ענן.** בלי תלות בבינארי חיצוני, כמו שעשינו ב-SQLite של הכדורגל.
7. **גיבוי = קובץ אחד.** `jewelry.db` מועתק לדרייב.

## 7. מה אני צריך ממך כדי לסגור סופית

1. **המפעל** — פנימי או חיצוני? כמה מפעלים/קבלני משנה? עובדים היום בוואטסאפ/אקסל?
2. **נפח** — כמה הזמנות פעילות בו-זמנית בממוצע? כמה לקוחות בשנה?
3. **מי עוד ייכנס למערכת** חוץ ממך?
4. **חשבוניות** — יש תוכנה קיימת (חשבונית ירוקה / iCount / רווית)? נשלב או נסתפק בתיעוד מספר חשבונית?
5. **מחיר זהב** — עדכון ידני יומי, או למשוך אוטומטית משער בינלאומי?
6. **מע"מ** — כל המחירים כולל או לפני?
7. **מה קיים היום** — אקסל? מחברת? יש נתונים לייבא?
8. **מלאי** — כמה סוגי חומרי גלם בערך? (משפיע על כמה כבד לבנות את שלב 5)

עונה על אלה — ואני מתחיל לבנות את שלב 1.
